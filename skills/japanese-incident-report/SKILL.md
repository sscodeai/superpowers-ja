# 日本向け障害報告・インシデント報告

## 目的

日本の IT 現場で使える障害報告を、事実、影響、対応、再発防止が追跡できる形で作成します。顧客向けには丁寧で簡潔に、社内向けには原因と改善 action を具体化します。

## 基本方針

- 推測と事実を分ける
- 時刻は JST で統一し、必要なら UTC も併記する
- 影響範囲は利用者、機能、件数、期間、データ影響に分ける
- 個人名の責任追及ではなく、仕組みとプロセスの改善に寄せる
- 暫定対応、恒久対応、再発防止を混同しない
- 顧客向け文面では未確定情報を断定しない
- 検証証跡、監視アラート、PR/MR、チケット、リリース履歴へリンクする

## 最初に確認すること

不足している情報がある場合、報告書を書き始める前に確認します。

- 報告対象: 顧客向け、社内向け、経営層向け、運用引き継ぎ向け
- 報告種別: 初報、続報、最終報告、RCA、再発防止計画
- 障害発生日時、検知日時、復旧日時
- 影響を受けた機能、利用者、取引、データ、外部連携
- 現在の状態: 継続中、暫定復旧、完全復旧、監視中
- 既に実施した対応、rollback、feature flag、手動補正
- 顧客名、案件名、チケット番号、連絡先、報告期限

## 初報テンプレート

初報は速さを優先します。原因が未確定の場合は、原因分析中と明記します。

```markdown
# 障害発生のご報告（初報）

## 概要

<YYYY-MM-DD HH:mm JST> 頃より、<対象サービス / 機能> において <事象> が発生しています。
現在、原因調査および復旧対応を進めています。

## 影響範囲

- 対象機能:
- 影響を受ける利用者:
- 影響期間:
- データ影響:

## 現在の状況

- 検知日時:
- 対応状況:
- 暫定回避策:

## 次回報告予定

次回は <YYYY-MM-DD HH:mm JST> を目安にご報告します。
```

## 続報テンプレート

続報では、変化した事実だけでなく、前回報告からの差分を明示します。

```markdown
# 障害対応状況のご報告（続報）

## 前回報告からの更新

- <更新 1>
- <更新 2>

## 現在判明している原因

<未確定の場合は「現在調査中」と記載>

## 実施済み対応

| 時刻 | 対応 | 結果 |
| --- | --- | --- |
| HH:mm | <対応内容> | <結果> |

## 残課題

- <残っている確認 / 対応>

## 次回報告予定

<YYYY-MM-DD HH:mm JST>
```

## 最終報告テンプレート

最終報告では、復旧、原因、影響、再発防止、検証証跡を揃えます。

```markdown
# 障害報告書（最終報告）

## 1. 概要

| 項目 | 内容 |
| --- | --- |
| 発生日時 | <YYYY-MM-DD HH:mm JST> |
| 検知日時 | <YYYY-MM-DD HH:mm JST> |
| 復旧日時 | <YYYY-MM-DD HH:mm JST> |
| 対象サービス | <service> |
| 重大度 | <Critical / High / Medium / Low> |
| ステータス | <復旧済み / 監視中> |

## 2. 影響範囲

- 対象機能:
- 影響利用者:
- 影響件数:
- データ影響:
- 外部連携影響:

## 3. 時系列

| 時刻 | 内容 | 証跡 |
| --- | --- | --- |
| HH:mm | <検知 / 対応 / 判断 / 復旧> | <alert / log / PR / ticket> |

## 4. 原因

### 直接原因

### 背景要因

### 検知が遅れた理由

## 5. 実施した対応

### 暫定対応

### 恒久対応

### データ補正

| No | 対策 | Owner | 期限 | 完了条件 |

- 監視確認:

- CI / CD:
```

## 原因分析の書き方

- 「設定ミス」「実装ミス」で止めず、なぜ検知・防止できなかったかを書く
- 5 Whys は形式化しすぎず、証跡で確認できる範囲に留める
- 外部要因がある場合も、自社側で取れる緩和策を分けて書く
- 再発防止策は「確認を徹底する」ではなく、自動化、監視、review gate、runbook 化へ落とす

避けたい表現:

```text
人的ミスにより発生しました。
今後は注意します。
問題ないことを確認しました。
```

推奨表現:

```text
レビュー時に migration の backward compatibility を確認する check がなく、
旧 version の batch が新 schema を読めない状態を検知できませんでした。
再発防止として、deploy 前 CI に backward compatibility test を追加します。
```

## 顧客向け表現

- 謝罪は簡潔にし、事実と対応を中心に書く
- 未確定事項は「確認中」「現時点では」と表現する
- 技術詳細は必要最小限にし、影響と復旧見込みを優先する
- 次回報告時刻を必ず書く
- 最終報告では、再発防止策の owner、期限、完了条件、関連リンクを空欄でも残す

```text
このたびはご迷惑をおかけし、誠に申し訳ございません。
現在、影響範囲の特定と復旧確認を進めております。
現時点で判明している内容は以下のとおりです。
```

## 完了前チェック

- 発生、検知、復旧の時刻が揃っている
- 影響範囲が機能、利用者、件数、期間、データ影響に分かれている
- 暫定対応と恒久対応が分離されている
- 再発防止策に owner、期限、完了条件がある
- 顧客向けに出せない内部情報、個人情報、secret、過度な責任表現が含まれていない
- 関連 ticket、PR/MR、監視、検証結果へのリンクがある
