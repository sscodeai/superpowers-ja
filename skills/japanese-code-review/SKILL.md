# 日本向けコードレビュー規約

## 目的

日本のチームでは、レビューコメントが丁寧すぎて重大度が伝わらない、逆に直截すぎて心理的安全性を下げる、という両方が起きます。この skill は「相手に配慮する」と「品質・安全性を曖昧にしない」を両立させるための参考です。

## 基本原則

- 人ではなくコード、仕様、リスクにコメントする
- 必須修正と任意提案を必ず分ける
- 仕様不明点は「質問」として残し、勝手に推測して approve しない
- 個人情報、権限、監査ログ、障害時運用は見落とさない
- チケット、設計書、CI、検証結果へのリンクを残し、後から追跡できる状態にする

## コメント重大度

| ラベル | 意味 | マージ判断 |
| --- | --- | --- |
| `[must]` | バグ、脆弱性、データ不整合、要件違反、監査上の問題 | 修正まで merge 不可 |
| `[should]` | 保守性、性能、テスト不足、運用リスク | 原則対応。今回外すなら理由を残す |
| `[nits]` | 命名、読みやすさ、軽微な表現 | 任意 |
| `[question]` | 意図、仕様、前提の確認 | 回答または仕様リンクが必要 |
| `[praise]` | 良い設計や改善点 | チーム学習のため残す |

## コメント例

```text
[must] 権限チェックが不足しています

この API は userId を指定して他ユーザーのデータを取得できるため、
ログインユーザーが対象データへアクセス可能か確認する必要があります。

確認観点:
- 管理者と一般ユーザーで期待結果が異なるか
- 監査ログに閲覧操作を残す必要があるか
- 既存の authorizeUserAccess() を流用できるか

Backlog: PROJ-1234
```

```text
[question] 文字コードは Shift_JIS 想定でしょうか?

CSV 出力は Excel で開く利用者が多い場合、UTF-8 BOM 付きまたは
Shift_JIS が必要になることがあります。仕様書に記載がなければ、
受入条件として明記したいです。
```

```text
[should] テストケースを追加したいです

今回の変更は請求金額に影響するため、少なくとも以下を追加したいです。
- 税率 8% / 10%
- 端数処理
- 割引適用後の合計
```

## 表現の指針

避けたい表現:

```text
ここはダメです。
なぜこうしたんですか?
普通はこう書きます。
```

推奨表現:

```text
ここはデータ不整合につながる可能性があるため、修正したいです。
この実装意図を確認させてください。
このケースでは既存の XxxService を使うと影響範囲を小さくできます。
```

## 承認前チェック

- チケットの受入条件を満たしている
- 仕様書、設計書、API 定義と矛盾していない
- DB migration、rollback、互換性を確認した
- 個人情報、権限、監査ログ、ログ出力の取り扱いを確認した
- テストが追加または更新され、CI が通っている
- エラーメッセージと運用ログが調査可能な粒度になっている
- リリースノート、手順書、環境変数、設定変更が必要なら記載済み

## Approve コメント例

```text
確認しました。受入条件、権限チェック、異常系テスト、CI 結果を確認済みです。
軽微な nits はありますが、今回のリリース判断には影響しないため approve します。
```
